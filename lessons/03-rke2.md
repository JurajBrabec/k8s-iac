# Lesson 3 — Bootstrap RKE2 with Ansible

**Time:** 3 hours. **Level:** intermediate. **Prerequisite:** Lesson 2; provisioned server and one to three worker VMs; instructor-approved RKE2/Rancher version matrix; Ansible Core, `jq`, SSH and `kubectl` available on the Linux workstation.

## Objectives and concepts

Terraform provisions the Proxmox VMs. Ansible then configures those hosts over SSH from a version-controlled, repeatable playbook. SSH remains the transport; participants do not log in to each VM to run the RKE2 installer and setup commands by hand. RKE2 installs as a systemd service. Argo CD is introduced later and manages Kubernetes resources, not the pre-cluster host bootstrap. A single RKE2 server with embedded etcd remains a single point of failure.

## Exercise

1. On the workstation, confirm Terraform knows the provisioned hosts and review their addresses:
   ```bash
   cd <COURSE_REPOSITORY>
   terraform -chdir=terraform/proxmox output node_addresses
   ```
   Verify each VM is reachable. If SSH prompts to trust a host key, verify its fingerprint using the instructor-approved method before accepting it. Confirm the Proxmox VM names result in unique guest hostnames.

2. Generate an Ansible inventory from Terraform's output and inspect its groups:
   ```bash
   bash scripts/generate-ansible-inventory.sh
   ansible-inventory -i ansible/inventory.generated.json --graph
   ansible -i ansible/inventory.generated.json all -m ansible.builtin.ping
   ```
   The inventory contains one `rke2_servers` host and the configured `rke2_workers`; it contains addresses, not join tokens or private keys. If your SSH key is not the default key or loaded in `ssh-agent`, configure `ANSIBLE_PRIVATE_KEY_FILE` for your workstation before proceeding.

3. Use the exact version approved in the instructor's compatibility matrix. Set it in the workstation environment, not in a node config or Git:
   ```bash
   export RKE2_VERSION='v<APPROVED_VERSION>+rke2r<N>'
   export ANSIBLE_CONFIG="$PWD/ansible/ansible.cfg"
   ansible-playbook -i ansible/inventory.generated.json ansible/site.yml --syntax-check
   ```
   Replace the placeholder with the complete version string. The playbook downloads the official RKE2 installer and invokes it with this pinned version. The instructor must review and rehearse the installer/version process; do not use `latest` for a repeatable lab.

4. Bootstrap the cluster from the workstation:
   ```bash
   ansible-playbook -i ansible/inventory.generated.json ansible/site.yml
   ```
   The playbook installs prerequisites and RKE2 on all hosts; configures the server TLS SAN; starts the server; obtains the server join token without displaying it; writes each worker config with root-only permissions; and starts the agents. It then copies a protected kubeconfig into the ignored `artifacts/` directory, rewrites its API address from loopback to the server address, and waits for the expected nodes to become `Ready`. Do not print, commit, or share that kubeconfig or the join token.

5. Inspect the results from the workstation:
   ```bash
   export KUBECONFIG="$PWD/artifacts/kubeconfig-lab"
   kubectl get nodes -o wide
   kubectl get pods -A
   ```
   Confirm one server and the configured number of workers are `Ready`; CoreDNS and CNI pods should be healthy. The server registration/supervisor endpoint is TCP 9345; the Kubernetes API is TCP 6443.

6. Rerun the same playbook without changing any input:
   ```bash
   ansible-playbook -i ansible/inventory.generated.json ansible/site.yml
   ```
   Check the recap for no unexpected changes. Configuration drift is reconciled; a different installed RKE2 version causes a clear failure rather than an implicit upgrade. Version upgrades should be planned and taught separately.

7. For troubleshooting, use the playbook's host groups with commands such as `ansible rke2_servers -i ansible/inventory.generated.json -b -m ansible.builtin.command -a 'systemctl status rke2-server'` or inspect `journalctl -u rke2-server`/`rke2-agent`. These are diagnostics, not the installation procedure. Do not copy tokens or kubeconfig contents into terminal transcripts.

8. The instructor installs the version-compatible ingress controller if it is not included in the cluster configuration. Verify `kubectl get ingressclass`, controller readiness and DNS for the application/Rancher hosts before Lesson 4.

## Acceptance

- Ansible completes from the workstation and creates the server and configured worker nodes without manually running installation commands on each VM.
- All expected Kubernetes nodes are `Ready`; core DNS/CNI pods are healthy; the generated kubeconfig is mode `0600` and ignored by Git.
- A second playbook run has no unexpected changes and does not print the registration token or kubeconfig.
- Explain the division of responsibility: Terraform manages VM infrastructure, Ansible bootstraps the OS services, and later Argo CD reconciles Kubernetes application manifests.
- Describe a production design with three RKE2 server nodes, stable API endpoint and independent backups; the training topology is not HA.

**Hints:** Use `ansible-inventory --graph`, `ansible ... -m ping`, `ansible-playbook -vv` (never use verbose output around secret-handling tasks), and `journalctl -u rke2-server`/`rke2-agent`. Check unique hostnames, firewall access to 9345/6443, version consistency, token permissions and the server IP in the kubeconfig. Never use `--start-at-task` to bypass the playbook's prerequisite checks.
